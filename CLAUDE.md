# CLAUDE.md — System Core Guidance

## WHAT

Root house — premium-уровня семейный архив: граф людей (Person) и
связей (Relationship) в основе, поверх которого строятся интерактивное семейное
дерево, профили людей, события, медиа (фото/видео/аудио/документы) и семейные
истории. Архитектурно готов к multi-tenant SaaS (несколько пользователей на
семью, роли, будущая подписка), но без преждевременной реализации billing/AI.

Stack: Next.js 16 (App Router), TypeScript strict, React 19, Drizzle ORM +
Neon Postgres, Auth.js v5 (database sessions), Tailwind CSS + shadcn/ui,
@xyflow/react (family tree visualization), Vercel Blob (media storage), Vitest.

Visual Target: Awwwards/FWA-уровень качества, но тёплый и спокойный «семейный»
тон — не enterprise CRM feel.

## WHY

- Awwwards/FWA visual quality — originality и motion над benchmark-показателями
- Core Web Vitals targets: Performance 85+ desktop / 75+ mobile, Accessibility 100, SEO 100, CLS 0.00
- Каждый интерактивный элемент имеет explicit hover/active/focus/loading states
- Zero generic или Bootstrap-style компонентов
- Тёплый, спокойный, «семейный» тон интерфейса — пользователь должен видеть
  «вот моя семья», а не «вот база данных Person entities»
- Доменная логика (Person/Relationship/Event/...) валидируется и авторизуется
  ИСКЛЮЧИТЕЛЬНО на сервере — клиентские проверки только для UX, никогда для security
- Родословная — это граф в БД (Person + Relationship), а не дерево; family tree,
  генограмма, timeline — разные UI-представления одних и тех же данных

## DESIGN TOKENS

Тёплая «семейная» палитра реализована (`src/app/globals.css`) — один тёплый
акцент (терракота, OKLCH hue 45), тёплые нейтральные (кремовый фон, тёплый
графитово-коричневый текст), НЕ стартаперский сине-фиолетовый градиент.
Generation color-coding в дереве — тот же hue, lightness/chroma по
`|generation|`-расстоянию от focus (см. DESIGN.md § Color Tokens для точных
значений и WCAG-проверки). Заголовки — Lora (`.font-heading`), UI — Geist
Sans; оба с кириллическим subset (весь интерфейс на русском).

Все цвета — только через `var(--color-name)`, никаких raw hex в компонентах.

## ANIMATION RULES

- Hardware acceleration ONLY: transform и opacity. Никогда top/left/width/height.
- will-change: transform, opacity — только на активно анимирующихся узлах
- Переходы focus-person в дереве — только transform (translate/scale),
  никогда полный re-layout всех nodes одновременно (stagger по расстоянию от нового focus)
- Всегда реализовывать `prefers-reduced-motion` fallback

## TREE LAYOUT RULES

Инварианты `src/domain/tree/tree-layout.builder.ts` (custom recursive layout,
не dagre/elk) — нарушение любого из них считается багом, даже если формальных
x-коллизий нет:

- **Линии-коннекторы никогда не пересекаются** — это главное правило.
  Пересечение линий читается как «перепутанное родство» даже когда каждая
  карточка технически на своём месте без коллизий.
- Но **карточки не должны накладываться друг на друга** — приоритетнее
  правила выше: если единственный способ развести две карточки без коллизии
  — визуально пересечь линии-коннекторы, коллизия карточек хуже, и лёгкое
  пересечение линий в этом редком случае допустимо.
- Дети всегда рядом со своими родителями — большой горизонтальный разрыв
  между родителем и ребёнком (на порядок больше обычного шага между
  карточками) — это баг, даже если сам по себе не создаёт коллизию.
- Предки мужа уходят строго в одну сторону (влево при муж-слева), предки
  жены — строго в другую (вправо) — линии двух родов никогда не
  перемешиваются между собой.
- Родные сиблинги (общие родители) должны располагаться рядом друг с другом,
  по возможности не перемежаясь карточками другой семьи/ветки.
- Между двумя НЕ связанными родством семьями/парами, случайно оказавшимися
  на одном горизонтальном уровне (например две независимые пары бабушек/
  дедушек), расстояние должно быть минимум в 2 раза больше стандартного
  зазора между супругами внутри одной пары — это визуально отделяет разные
  роды друг от друга даже когда они формально не пересекаются.
- Супруги должны быть всегда вместе (husband-left/wife-right, стандартный
  зазор между ними) — при разрешении коллизий в других частях дерева нельзя
  разводить пару в стороны, даже если это временно проще; если чья-то ветка
  сдвигается, супруг(а) сдвигается вместе с ней.
- Фокус-персона всегда в центре (x=0), от неё дерево строится вправо/влево.
- При отладке layout-багов — сначала воспроизводить на РЕАЛЬНЫХ данных из
  Neon (`getFocusTreeLayout`), а не только на синтетических fixtures:
  синтетические репро могут случайно не задеть нужную комбинацию условий.

### tree-v4 (`src/domain/tree-v4/`)

Независимая реализация (не переиспользует layout tree-v2/tree-v3), свой
набор инвариантов:

- Родной сиблинг фокус-персоны (общие родители) должен стоять рядом с самой
  фокус-персоной, вплотную к её карточке — а не «через» её супруга/супругу,
  даже если место сразу за супругом(ой) технически первое свободное и
  коллизий не возникает. Пример: у Александра есть жена Элеонора и родная
  сестра Дарья — Дарья должна оказаться прямо рядом с Александром (с той
  стороны, где нет Элеоноры), а не за Элеонорой. Геометрическая
  бесколлизионность не оправдывает разрыв кровного родства чужим человеком
  визуально между сиблингами.
- Родители должны быть выровнены по центру ВСЕГО ряда своих детей — не
  только по позиции того ребёнка, который оказался размещён первым (обычно
  фокус-персоны). Если у фокуса есть сиблинг (например, у Александра —
  Дарья), пара родителей (Виктор+Галина) центрируется над серединой между
  Александром и Дарьей, а не над одним Александром. Фокус-персона остаётся
  неподвижным якорем координат (x=0) — выравнивание всегда достигается
  сдвигом РОДИТЕЛЕЙ под готовый ряд детей, а не сдвигом уже зафиксированных
  детей под родителей. Практически это значит: все ещё не размещённые
  сиблинги фокуса нужно разместить ДО вычисления итоговой позиции их общих
  родителей, иначе родители зафиксируются над неполным рядом.
- **Супруги всегда рядом (стандартный `SPOUSE_GAP`) — это приоритетнее
  прямой линии к прародителям.** Если у обоих супругов на одном уровне
  (например, у Виктора и Галины) есть СВОИ собственные родители, каждой
  паре прародителей нужно ~384px ширины (2 карточки + spouse gap) плюс
  `INTER_FAMILY_GAP` между двумя несвязанными кластерами — этого места
  часто не хватает, если сами супруги стоят вплотную друг к другу.
  ЗАПРЕЩЕНО решать эту нехватку раздвиганием самих супругов (Виктора и
  Галины) шире стандартного зазора — это ломает более важное правило
  «супруги — компактная визуальная единица» ради второстепенного «линия
  к прародителям идёт без изгиба». Было реализовано и отменено: попытка
  через `measureAncestorHalfWidth`/расширенный `spouseGap` в
  `placeAncestorUnit` (`placement.ts`) раздвигала Виктора и Галину почти
  вдвое шире обычного — это неприемлемо, даже если линии к прародителям
  становились идеально прямыми.
- **Если из-за компактности супругов обеим парам прародителей не хватает
  места — дефицит делится ПОПОЛАМ между обеими парами симметрично, а не
  достаётся только одной стороне.** Первая реализация центрирования была
  «жадной»: пары обрабатывались по очереди (paternal раньше maternal, по
  `sideRank`), первая обработанная получала идеальный центр, а вторая
  целиком поглощала весь дефицит через collision-avoidance — визуально это
  давало «у Купчиков линия прямая, у Козловских — с изгибом», что
  пользователь явно отверг: это не центрирование, а обслуживание в порядке
  очереди. Правильно: у ОБЕИХ пар прародителей вычисляется идеальный
  (несмещённый) центр ДО какого-либо резервирования места на этой строке
  поколения; если идеальные интервалы двух соседних пар пересекаются, обе
  сдвигаются на равное расстояние от общей середины в противоположные
  стороны — если излом неизбежен, он одинаковый у обеих линий, а не «одна
  прямая, вторая кривая». Реализовано в `placement.ts`:
  `resolveSymmetricOverlaps` вычисляет и корректирует `idealX` для всех
  ещё не размещённых пар прародителей одной строки-поколения ДО вызова
  `placeAncestorUnit`, который затем только резолвит настоящие коллизии
  занятого места (branch-direction поиск), а не сам решает, куда «тянуться»
  по умолчанию. Важное следствие: если у одной пары прародителей МНОГО
  детей (например, у Николая+Елизаветы — Виктор, Николай-мл., Светлана,
  Наталья), а у другой пары — один ребёнок (у Козловских — только Галина),
  асимметрия в итоге ОСТАЁТСЯ — пара с большим рядом детей центрируется
  над серединой ВСЕГО своего ряда (см. следующий пункт), а не над одним
  ребёнком, и это законно тянет её сильно в сторону от партнёра по этой же
  строке. Симметричное распределение (этот пункт) решает только конфликт
  «чья пара прародителей получает идеальный центр первой», а не выравнивает
  пары с разным числом детей друг под друга искусственно.
- **Родной бездетный сиблинг родителя (например, у Виктора — братья/
  сёстры Николай-мл., Светлана, Наталья) НИКОГДА не должен обрабатываться
  как самостоятельный «предковый юнит», который сам себе ищет позицию по
  умолчанию у x=0.** Такой сиблинг не имеет собственных детей, поэтому
  `preferredAncestorX` не находит, куда его "тянет", и он получает
  idealX=0 — если после этого его пропустить через обычный
  `placeAncestorUnit`/`resolveSymmetricOverlaps`, он будет искать свободное
  место рядом с началом координат и может улететь на сотни/тысячи px от
  своего кровного родственника (Виктора), с которым должен стоять рядом.
  Было реализовано и исправлено: строка-поколение (`placeAncestors` в
  `placement.ts`) теперь исключает из списка «предковых юнитов» любого
  человека, у которого НЕТ собственных уже размещённых потомков
  (`preferredAncestorX` возвращает null и для него, и для его супруга) И
  есть хотя бы один сиблинг в графе — такие люди размещаются исключительно
  через `placeUnplacedSiblings`, привязанные к уже размещённому кровному
  родственнику, точно так же как Дарья рядом с Александром, только на
  уровень выше.
- **Порядок пар прародителей внутри `resolveSymmetricOverlaps` ДОЛЖЕН
  соответствовать их РЕАЛЬНОЙ тяге (idealX), а не алфавитному порядку id.**
  Функция трактует units[i] как «левее» units[i+1] и раздвигает их именно в
  этом порядке — если массив упорядочен как-то иначе (например, по id, как
  изначально сортировался `peopleInRow` для решения «кто чей сосед по
  строке»), пара с реальной тягой правее может оказаться сдвинута ЛЕВЕЕ
  пары с тягой левее — линии-коннекторы перекрещиваются друг с другом,
  хотя ни одна пара по отдельности ни с чем не коллизирует. Баг проявился
  на двух парах ОДНОЙ ветки (обе «paternal»): Владимир+Марфа (тянутся к
  Николаю, который левее) и Григорий+Елизавета Кривуша (тянутся к
  Елизавете, которая правее) — из-за алфавитного id (`elizaveta-krivusha`
  раньше `marfa-kupchik`) Кривуша обрабатывались как «левая» пара, хотя их
  реальный ребёнок правее. Пользователь поймал это по скриншоту:
  «ты перепутал местами семьи кривуш и купчик!». Исправлено: в
  `placement.ts` массив `units` сортируется по `idealX` (`units.sort((a, b)
=> a.idealX - b.idealX)`) непосредственно ПЕРЕД вызовом
  `resolveSymmetricOverlaps` — сортировка по `sideRank`/id в `peopleInRow`
  остаётся (она нужна для другого: paternal-строки перед maternal), но
  массив, который реально раздвигается «влево/вправо», обязан быть
  отсортирован по фактической предпочитаемой позиции, а не по имени.
- **Родные сиблинги ФОКУС-ПЕРСОНЫ (например, Дарья рядом с Александром)
  должны занимать своё место РАНЬШЕ любых других веток на той же
  generation-строке — даже двоюродных, троюродных и т.д.** Generation
  считается по BFS-расстоянию от фокуса, а не по кровной близости — значит
  внуки/правнуки двоюродных сиблингов фокуса (например, внуки Светланы и
  Натальи через их детей Ольгу/Юрия и Егора/Анастасию) могут оказаться
  ровно на том же уровне (y), что и родная сестра фокуса. Раньше строка
  поколения фокуса обрабатывалась общим циклом `placeAncestors`, где
  порядок внутри строки определялся id — и если чья-то двоюродная ветка
  сортировалась раньше по алфавиту (например, «natalya-kupchik» и
  «svetlana-kupchik» раньше «viktor-kupchik»), их внуки успевали занять
  место рядом с фокусом ДО того, как родная сестра фокуса вообще получала
  свою очередь — она улетала на сотни px дальше в поисках свободного места.
  Пользователь не сообщал об этом явно, баг найден и исправлен
  проактивно при добавлении Виктора Ефимовича (мужа Светланы) и его детей.
  Исправлено: в `placeAncestors` (`placement.ts`) в самом начале, ДО
  основного цикла по generation rows, вызывается
  `placeUnplacedSiblings(focusSiblingIds(graph), y=0, ...)` — родные
  сиблинги фокуса резервируют своё место первыми, независимо от того,
  сколько других веток есть на этой же строке и в каком порядке их
  обрабатывает основной цикл. Кровная близость к фокусу всегда важнее
  порядка обхода id.
- **Человек, у которого в графе НЕТ вообще ни одного кровного родителя
  (`parentIds.length === 0`) — например, супруг(а), вошедший(ая) в семью
  браком, чьи собственные предки в данных не записаны (Виктор Равбецкий,
  муж Марины) — НИКОГДА не должен рассматриваться как самостоятельный
  «предковый юнит», если его/её не тянут вверх его/её СОБСТВЕННЫЕ уже
  размещённые потомки.** Проверка `!hasSiblingInGraph(id)` (для исключения
  бездетных кровных сиблингов, см. пункт выше) сама по себе возвращает
  `true` и для такого супруга — у него просто нет `parentIds`, чтобы вообще
  проверить сиблингов — из-за чего он ошибочно проходит фильтр и
  обрабатывается как независимый юнит с `idealX=0` через
  `placeAncestorUnit`, ДО того как через `placeUnplacedSiblings` вообще
  дойдёт очередь до его настоящей кровной жены/мужа. Баг: после того как у
  Марины появились собственные дети, её муж Виктор Равбецкий (без
  `parentIds`) стал проходить фильтр и размещался первым, утаскивая всю
  строку сестёр Галины в середину чужого кластера (сиблингов Виктора
  Купчика) вместо места рядом с Галиной. Исправлено в `placement.ts`:
  добавлена проверка `isParentlessInLawWithNoPull` — человек без
  `parentIds` И без собственной тяги потомков (`isPulledByOwnDescendants`
  ложно) исключается из `peopleInRow` независимо от результата
  `hasSiblingInGraph`; человек без `parentIds`, но РЕАЛЬНО подтянутый
  своими потомками (например, Юстин Купчик — SoloParent-предок без своих
  родителей в данных, но с сыном Владимиром) по-прежнему обрабатывается
  нормально — критерий именно «нет и своей тяги», а не просто «нет
  родителей».
- **`placeUnplacedSiblings` обязана резервировать ПОЛНУЮ ширину юнита (обе
  карточки + `SPOUSE_GAP`) для сиблинга, у которого уже есть супруг(а), а
  не только `CARD_WIDTH` для его/её собственной карточки.** Иначе место,
  которое реально нужно этому супругу, может быть первым же свободным
  слотом следующего кровного сиблинга в этой же строке — и тогда
  `growPersonDescendants`, пытаясь вырастить супруга, находит место уже
  занятым и уходит в поиск на тысячи px в сторону, разлучая пару. Баг:
  Марине резервировался только один слот между Ниной и остальным рядом;
  её муж Виктор Равбецкий (обязан стоять СЛЕВА от неё — male < female по
  `shouldBeLeft`) пытался занять место слева от Марины, находил там уже
  поставленную Нину и улетал на другой конец дерева. Исправлено:
  `placeUnplacedSiblings` теперь вычисляет `unitWidth = spouseId &&
!positionByPerson.has(spouseId) ? CARD_WIDTH*2+SPOUSE_GAP : CARD_WIDTH`
  для кандидатного слота (как `placeAncestorUnit` делает для пары предков),
  и ставит саму карточку сиблинга на нужную половину этого слота согласно
  `leftPersonId`/`rightPersonId` партнёрства — освобождая вторую половину
  именно там, где `growPersonDescendants` её и найдёт.
- **Зазор между двумя КРОВНЫМИ сиблингами должен оставаться ровно
  `SIBLING_GAP`, даже если у одного из них есть свой супруг — лишняя
  ширина супружеской пары обязана уходить на ДАЛЬНЮЮ от кровного соседа
  сторону, а не незаметно раздувать сам кровный зазор.** Первая версия
  фикса выше (резервирование `unitWidth` под сиблинга-с-супругом)
  резервировала слот, центрированный на `anchorX ± (unitWidth +
SIBLING_GAP)` — раз карточка самого сиблинга стоит только на БЛИЖНЕЙ
  половине этого слота, около половины `unitWidth` лишнего места случайно
  доставалось именно кровному зазору (Светлана↔Николай-мл. рендерились на
  ~168px друг от друга вместо обычных 64px), хотя должно было уйти на
  зазор супруг↔сосед с другой стороны (Виктор Ефимович↔Наталья — там оно
  и уместно, это разделение двух разных семей). Пользователь поймал через
  скриншот: «между сиблингами явно не то расстояние». Важное следствие
  при исправлении: карточка сиблинга должна располагаться на той же
  стороне от anchor, что и раньше (ряд растёт в ОДНУ сторону
  последовательно — так же, как до этого фикса), НЕЛЬЗЯ переключать
  направление роста ряда только потому, что у конкретного сиблинга
  супруг(а) должен(на) стоять с другой стороны (male<female) — первая
  попытка исправить именно так и сделала, что улетело целым рядом сестёр
  Галины влево вместо продолжения вправо. Иногда СУПРУГ неизбежно
  оказывается МЕЖДУ двумя кровными сиблингами (например, муж Марины
  Виктор Равбецкий обязан быть слева от неё, а Марина стоит справа от
  Нины по направлению роста ряда) — в этом единственном случае кровный
  зазор законно расширяется, чтобы вместить супруга + `SPOUSE_GAP`, но
  это исключение только когда неизбежно, а не правило по умолчанию.
  Исправлено в `placeUnplacedSiblings` (`placement.ts`): направление
  (`leftFree`/`rightFree`) определяется как и раньше, а расширение зазора
  применяется только если требуемая сторона супруга указывает НА anchor
  (`spouseTowardAnchor`), а не от него.

## CODE RULES

- TypeScript strict — zero `any` типов
- Компоненты: максимум 150 строк — разбивать на под-компоненты при превышении
- Никаких raw hex цветов — всегда `var(--color-name)`
- Никаких inline styles, кроме динамических вычисляемых значений
- Все изображения: next/image с blur placeholder и явными width/height
- Только семантический HTML: `<main>`, `<section>`, `<article>`, `<nav>`, `<header>`, `<footer>`
- Никаких `console.log` в закоммиченном коде
- `src/domain/**` НЕ импортирует `next`/`react` — юнит-тестируется изолированно от фреймворка
- Каждый server action в `src/actions/**` начинается с `auth()` →
  `requireFamilyAccess(familyId, userId, minRole)` до любого чтения/записи
- Каждый repository-метод `getById`-типа фильтрует `WHERE id = ... AND family_id = ...`
  в одном запросе — подмена id из чужой Family должна возвращать `null`, а не
  «нашли, но потом отказали»

## FORBIDDEN

- Generic Bootstrap-style компоненты
- Default CSS ease или linear easing curves
- Layout-shifting свойства в анимациях (top, left, height, width)
- setTimeout для анимационных задержек — использовать delays анимационной библиотеки
- Raw hardcoded цвета или spacing-значения — всегда CSS-переменные
- Резолвить Person/Media/Event/Story по id без `family_id` в WHERE-условии того же запроса
- Импорт `@xyflow/react` где-либо вне `src/components/tree/`
- Доверять client-переданной роли/правам доступа без сверки в `requireFamilyAccess`
- `db.transaction(...)` — `neon-http` драйвер не поддерживает транзакции; для
  атомарных multi-table операций использовать один SQL-стейтмент с CTE
  (см. `family.service.ts::createFamily`, `docs/architecture.md`)
